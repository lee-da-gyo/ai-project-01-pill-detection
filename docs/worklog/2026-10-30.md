## 한 일
### 원본 라벨 오류 4장 발견·수정
- 1:1 매칭으로 달라진 4건과 "학습한 약을 신뢰도 0.96~0.98로 틀렸다"는 사례를 원본 사진과 대조했다. 모델이 맞고 **라벨이 틀린** 경우였다.
  - 3장: 다른 약 두 개가 **같은 좌표**에 라벨되고, 알약 하나는 라벨이 없었다.
  - 1장: 두 알약의 약 코드가 **서로 바뀌어** 있었다.
- 같은 조합의 다른 각도 사진과 생김새를 비교해 확정했다. 남은 학습 가능 오분류·놓침 21건은 라벨이 맞았다.
- 정제 코드에 감사 두 개를 추가했다.
  - D: 다른 약 박스끼리 IoU ≥ 0.9이면 후보로 표시한다. 데이터만 보는 감사다.
  - E: OOF 예측이 정답과 신뢰도 0.9 이상으로 다르게 답하면 후보로 표시한다. 모델 예측을 쓰는 사후 감사다.
- 후보는 자동으로 고치지 않는다. 사람이 확인한 결정(`configs/label_review.csv`)만 적용한다.
- 무결성 검사에 "다른 약끼리 같은 좌표 0"을 추가했다.
- 리뷰 지적을 받아 결정 기록 형식을 바꿨다. 결정마다 ID, 검수자, 검수일, 검수 때 본 두 박스의 좌표를 적는다.
  - 현재 라벨이 그 좌표와 같을 때만 적용하므로, 다시 적용해도 라벨 교환이 원상복귀하지 않는다.
  - 실제로 겹친 알약은 keep_overlap으로 남길 수 있다.
- 형식 검사와 경계 사례(미확정 결정, 좌표 불일치, 박스·알약 수 불일치)를 테스트했다.
- 재검토 지적을 받아 두 가지를 더 고쳤다.
  - keep_overlap도 검수 때 본 좌표 그대로일 때만 겹침을 허용한다. 두 박스가 함께 다른 곳으로 옮겨진 겹침은 새 후보로 잡힌다.
  - 감사 후보에는 정확히 같은 두 약 쌍의 결정만 붙인다. 같은 박스를 고친 다른 쌍의 결정은 "관련 결정"으로 구분해 적는다.
  - 데이터 준비를 다시 돌려 정제 결과와 fold가 그대로임을 확인했다.
- 3차 재검토 지적을 반영했다.
  - 감사 스크립트가 Windows 기본 콘솔(cp949)에서 대시 문자 때문에 멈췄다. 콘솔에 찍는 문자열의 cp949 밖 문자(대시, 경고 기호)를 모두 바꾸고, 이를 검사하는 테스트를 추가했다. 인코딩 설정 없이 실행해 정상 종료를 확인했다.
  - 결정이 없는 후보를 "기각"으로 표시하던 기본값을 "미검토"로 바꾸고, 미검토 후보가 있으면 감사 스크립트가 실패로 끝나게 했다. 라벨이 맞다는 기각은 keep_label 결정으로만 남긴다.
- 4차 재검토 지적을 반영했다.
  - 감사 출처를 예측 파일 해시 하나에서 예측 · 입력(원본 라벨 · 이미지 · fold · 검수 결정) · 코드 세 묶음의 manifest 해시로 넓혔다.
  - 검수 결정 파일에 의미 검사(규칙별 허용 결정, 같은 약 코드, 빈 검수 정보, 날짜 형식, 좌표 범위)를 추가했다.
  - 스크립트 설명(--help 출력)의 대시도 기본 콘솔에서 멈추지 않게 바꿨다.
  - 테스트 기록(reports/logs/pytest.log)을 다시 만들었다. 테스트 함수 35개, 매개변수 포함 37개 케이스가 통과했다.
- 감사 결과에 출처(실험 이름, WBF 가중치·IoU, 예측 파일 해시)를 남겼다. 수정 전 1:1 감사는 E 4건, 수정 후 2:1 재감사는 E 5건이고, 늘어난 1건은 이미 고친 박스였다.
- 박스 수는 771개(원본 763 + 누락 추가 8) 그대로이고, 수정 기록은 10건 → 15건(이동 4 · 교환 2 포함)이 되었다. 분할(`folds.csv`)은 바뀌지 않았다.

### 전체 재학습 (5-Fold 15회 + 최종 모델 2개)
- 라벨이 바뀌었으므로 11s·11m·CLAHE 5-Fold와 최종 모델을 모두 다시 학습했다. 이전 결과는 `runs/_before_label_fix/`에 보관했다.

| 37종 조건부 OOF mAP50-95 | 수정 전 | 수정 후 |
|:---|---:|---:|
| YOLO11s | 0.941 | 0.956 |
| YOLO11m | 0.936 | 0.941 |
| WBF 11s + 11m | 0.954 (1:1) | 0.964 (2:1) |

- 수정 전후 차이를 "정제 효과"로 쓰지 않는다. 평가 정답도 함께 바뀌었으므로, 수정된 라벨에서 새로 잰 추정치로만 보고한다.
- **WBF 설정이 1:1 → 2:1로 바뀌었다.** 같은 절차(근사 메타 검증)를 다시 돌리자 보류 fold 5개 모두에서 2:1이 뽑혔다. 절차를 고정하고 결과를 따랐다. IoU는 3개 fold에서 0.7, 2개 fold에서 0.6이 뽑혔다.
- 최종 모델 에포크도 같은 규칙(fold별 best epoch 중앙값)으로 다시 계산해 11s 50 → 80, 11m 83 → 80으로 바꿨다.

### 학습률 실험 (R11)
- optimizer=auto가 실제로 고른 값은 AdamW, lr0 0.000167이다. 이것을 기준으로 3배·0.3배만 바꿔 fold 0에서 비교했다.
- 판단 규칙은 실행 전에 설정 파일에 적어 두었다: "E0보다 0.005 이상 좋을 때만 5-Fold로 확인한다."

| 학습률 | fold 0 mAP50-95 | E0 대비 |
|:---|---:|---:|
| 0.000167 (E0) | 0.8356 | – |
| 0.0005 (3배) | 0.8381 | +0.0025 |
| 0.00005 (0.3배) | 0.8269 | −0.0087 |

- 3배는 기준에 못 미치고, 0.3배는 떨어졌다. 그래서 auto 값을 유지한다.

## 발견한 문제 (인사이트)
- **검사 항목을 "가능한 오류 유형"에서 출발해 정해야 한다.** 처음 무결성 검사는 "같은 약 중복"만 보고 "다른 약끼리 같은 좌표"를 놓쳤다.
- **모델 예측으로 찾은 라벨 오류 후보는 모델이 같이 틀린 오류를 놓친다.** 그래서 탐지 재현율을 알 수 없다고 명시했다. 데이터만 보는 D와 구분해 기록했다.
- **선택 절차를 고정하면 결과가 바뀌어도 흔들리지 않는다.** 라벨 수정 뒤 WBF 가중치와 에포크가 바뀌었지만, 같은 규칙을 다시 적용했을 뿐이라 설명이 쉽다.
- 백그라운드 대기열을 중지했다고 생각했는데 프로세스가 남아, 같은 학습이 두 번 동시에 돌았다. 프로세스 목록으로 확인한 뒤 둘 다 끄고 하나만 다시 돌렸다. 중지 후에는 반드시 프로세스 목록으로 확인한다.

## 고민 / 결정
- 라벨 수정 후 재학습 범위: fold 0만 다시 돌리면 5-Fold 결론과 섞인다. 그래서 5-Fold 전체와 최종 모델을 다시 학습했다.
- 라벨 수정 전 fold 0 탐색(E1~E3, 2단계, 분류기, Copy-Paste)은 다시 돌리지 않았다. "라벨 수정 전 기록"으로 표시하고, 최종 수치와 직접 비교하지 않는다.
